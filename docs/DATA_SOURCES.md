# Data Sources — eRTMAC-NWIS

Phase 18 deliverable. Every record in MongoDB carries a `source` (free text) and `sourceType`
(enum) field. This document is the authoritative map from `sourceType` to what that data
actually is, so nobody — developer, judge, or future maintainer — can mistake one category
for another. See `docs/FRONTEND_INTEGRATION_ANALYSIS.md` §9 for how this was determined and
`docs/BACKEND_API_CONTRACT.md` for how it's exposed via the API.

## `sourceType: "public_document"`

**5 real PDF files** in `data/raw/oil_india/`, provided directly by the team — not fabricated
or downloaded by any agent in this project:

| File | Size | Apparent subject (per filename; confirmed only after Phase 4 extraction) |
|---|---|---|
| `1_OCS_Bhogpara_0.pdf` | 13.4 MB | Oil Collection Station, Bhogpara |
| `2_Doomdoma_Pengry.pdf` | 2.6 MB | Doomdoma–Pengaree facility |
| `3_GCS_hebeda_FGGS_Chabua_GMS_Tengakhat_GCS_0.pdf` | 84.2 MB | Group Collection Station / Flare Gas Gathering Station / Group Metering Station — Hebeda, Chabua, Tengakhat |
| `4_Ningru_0.pdf` | 4.9 MB | Ningru facility |
| `11_Moran_1.pdf` | 11.4 MB | Moran facility |

These are **facility-level environmental/regulatory documents**, confirmed by running Phase
4 extraction against `4_Ningru_0.pdf` (79 chunks indexed): content includes environmental
impact assessment language (noise/soil quality impacts from drilling rigs and ancillary
equipment), well plugging and site-abandonment procedures, and references to Government of
India Gazette notifications governing groundwater/exploratory well drilling. **They are not
WCR/DDR-style well completion or daily drilling reports** — no individual well coordinates,
drilling depths, formation tops, or incident logs were found. This confirms the Phase 0
hypothesis: these are Environmental Clearance-type filings for OIL India facilities, not
per-well technical records. The other 4 PDFs have not all been extracted yet but are
presumed to be the same document type given matching filename conventions; re-verify per
document before relying on this for a specific query. They are registered in the
`documents` collection by `app/db/seed.py`; indexing (text extraction → chunking →
embedding) happens per-document via `POST /api/documents/index`.

## `sourceType: "government_data"`

**1 real CSV**, `data/raw/government/PNG_Statistics_2020-21_Table2.3_0.csv` — a national
aggregate table (23 rows) of flowing-oil-well counts by operator (ONGC, OIL, PSC/RSC/CBM
regime) and state (Gujarat, Rajasthan, Assam & Arunachal Pradesh, Tripura, Andhra Pradesh,
Tamil Nadu, West Bengal, Jharkhand, Madhya Pradesh, others). No individual well identities,
coordinates, or depths — useful only for state/operator-level context, e.g. in
`/api/analytics/*` if a national-comparison widget is ever added.

## `sourceType: "geospatial_data"`

**1 real OpenStreetMap extract**, `data/raw/geospatial/assam.pbf` (59 MB) — the base map
layer (roads, settlements, administrative boundaries) for Assam. Contains **no oil-well
point data of any kind**. It's the geography the map is drawn on, not a well database.

## `sourceType: "synthetic_demo"`

**Every well, formation, historical incident, alert, and telemetry reading currently
rendered by the frontend.** All of it originates from `src/data/wellsData.ts` and
`src/data/historicalRiskTrends.ts` — fixtures generated by the original Google AI Studio
agent that scaffolded this app (see `metadata.json`), not from any Oil India system or
document. This includes every well name pattern seen in the UI (`NWIS-*`, `Selt-OW-*`,
`OIL-*`), every WCR/DDR "citation" with its page numbers and OCR-confidence figures, and
every predictive alert.

**Why this data still exists in the backend at all**, rather than being deleted: the
frontend is locked (cannot be redesigned), and its map, dashboards, and demo scenarios are
built entirely around these specific wells and incidents. Deleting them would break the UI.
Per the team's explicit decision (`docs/BACKEND_API_CONTRACT.md`), these are seeded verbatim
into MongoDB and **indexed into the RAG corpus** (as `document_chunks` with
`sourceType: "synthetic_demo"`) so the AI Assistant can still answer the kind of
nearby-wells questions the frontend's own demo scenarios ask — but every response and every
citation it produces from this data visibly carries `sourceType: "synthetic_demo"`, and
nothing in this codebase ever describes it as a real Oil India record.

`app/db/seed.py` is the single place this data enters MongoDB. It reads
`app/db/seed_data/frontend_fixtures.json`, produced by running
`npx tsx scripts/export_frontend_fixtures.ts` from the repo root (a read-only export of the
frontend's own TypeScript modules — it does not modify `src/`).

Also in this category: the 4 preset demo operator accounts (`src/types/auth.ts`
`PRESET_USERS`), seeded into the `users` collection with a **shared, clearly-marked
dev/demo-only password** (`ChangeMe123!`, set in `app/db/seed.py` — not committed anywhere
as a secret since it's intentionally public knowledge for local demo use; rotate before any
non-local deployment). Real password authentication is still enforced — this is a seeded
credential, not an authentication bypass.

## `sourceType: "derived"`

Anything computed or uploaded after the fact: a document a user uploads through
`POST /api/documents/upload` (until explicitly re-tagged), and any future aggregate/analytics
record computed from the above sources rather than sourced directly.

## What this means for the demo (Phase 17)

- Map, well list, historical events tab, and predictive alerts: unchanged from today's UI —
  all backed by `synthetic_demo` data seeded verbatim, so visually nothing regresses.
- AI Assistant (`/api/rag/chat`): can answer both "what happened in nearby wells"-style
  questions (grounded in labeled `synthetic_demo` chunks) and questions actually answerable
  from the 5 real PDFs (grounded in `public_document` chunks, once Phase 4/6 index them) —
  every citation in the response shows which kind of evidence it is.
- A question with no supporting evidence in *either* corpus returns
  `isInsufficientInfo: true` — never a fabricated answer, regardless of which corpus would
  have been expected to contain it.
